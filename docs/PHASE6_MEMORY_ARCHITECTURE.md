# Phase 6 Memory Architecture

Status: audit and architecture only. Do not implement Phase 6B/6C/6D from this
document until that phase is explicitly started.

Baseline inspected:

- Commit: `cf65074 feat: add verified Gmail draft action`.
- Existing untracked paths intentionally ignored: `agentforge_prephase1/`,
  `data/eval/diagnostics/`, `docs/GOAL_EXECUTION_SYSTEM.md`.
- Current design principle: reuse the mechanisms that already exist before
  adding tables, modules, jobs, dependencies, or model calls.

North star:

```text
Store broadly, retrieve selectively, send minimally.
Optimize for minimum sufficient context, not simply minimum context.
LLM proposes; deterministic code disposes.
```

## 1. Current memory architecture

AgentForge already has four different lifetimes of state. They should not be
collapsed into one "memory" abstraction.

### Working memory

Current task/step execution is mostly durable Postgres state, with only minimal
LangGraph state:

- `AgentState` in `src/agentsys/graph/state.py` carries only `task_id` and
  transient `route`.
- `Task` stores the user request, owner, status, final output, eval flag, and
  timestamps.
- `Subtask` stores step position, description, assigned tool, success criteria,
  status, output, attempt count, and timestamps.
- `ToolCall` is the Phase 3 execution ledger, including inputs, outputs,
  success/null ambiguity, latency, and `effect_key`.
- `Review`, `Escalation`, `TraceSpan`, and `LlmCall` provide review, human
  pause/resume, trace, and token/cost records.

Redis-backed task scratch state lives in `src/agentsys/memory/short_term.py`.
It is a generic per-task key namespace, `task:{task_id}:mem:{field}`, with
JSON `set/get` helpers and list append/read helpers. It currently supports:

- `UNPRODUCTIVE_FIELD` in `graph/nodes.py`.
- `deadcalls.py` failure and repeated-success ledgers.
- Google Photos picker session reuse in `tools/google_photos.py`.

Other Redis users are not memory in the cognitive sense:

- auth session cache,
- idempotency keys,
- cancellation flags,
- rate limits,
- OAuth state,
- event pub/sub.

Expiration:

- `short_term.clear(task_id)` runs after `synthesize_node` completes a full
  task and wipes task scratch state.
- Task scratch keys have no TTL in `short_term.py`; failed/cancelled tasks can
  leave scratch keys behind until manual cleanup or Redis eviction.
- Auth/session/idempotency/rate-limit/OAuth keys have their own TTL behavior in
  their owning modules.
- LangGraph state expires at the end of one `graph.invoke()` call.
- Postgres task/subtask/tool/review/escalation/trace/LLM rows do not expire.

### Conversation memory

Conversation storage is append-only but asymmetric:

- `Task.request_text` is the original user request.
- `TaskMessage` stores user-authored follow-ups after a task is terminal.
- Assistant turns are not stored as `TaskMessage` rows. They are reconstructed
  from `TraceSpan` rows whose `span_type` is `synthesize` or `quick_reply` and
  whose output contains `final_answer`.

`_gather_conversation_history(task_id, task)` in `graph/nodes.py` reconstructs
conversation history by interleaving:

- original request,
- all `synthesize`/`quick_reply` final answers,
- all user follow-ups.

Current send behavior:

- First turn: no conversation block is sent; `request` carries the original
  request.
- Continued conversation: the entire reconstructed conversation is sent. There
  is no last-N limit, no rolling summary, no token threshold, and no truncation
  in `_gather_conversation_history`.
- Quick replies use the same full conversation reconstruction.
- `TaskMessage.role` is always `user` today.

### Prior task context inside a task

`_gather_prior_context(task_id, current_subtask_id=None)` is task-local context,
not long-term memory. It currently:

- reads subtasks in this task with status `DONE`, `FAILED`, `ESCALATED`, or
  `SKIPPED`;
- excludes the current subtask;
- keeps the last `settings.context_recent_steps_full` steps verbatim;
- truncates older long outputs to `settings.context_older_step_chars`;
- leaves full outputs in Postgres and relies on artifact spill pointers for
  oversized tool outputs.

This is an important current fix: older architecture notes said only `DONE`
steps were visible, but current code includes failed, escalated, and skipped
steps too.

### Existing long-term memory

Long-term memory is split between Postgres and Chroma:

- `MemoryEntry` in Postgres stores structured metadata:
  `id`, `owner_id`, optional `task_id`, `kind`, `content`, `importance`,
  `created_at`, `last_accessed_at`.
- Chroma collection `agent_long_term_memory` stores:
  document text, embedding, and metadata:
  `kind`, `task_id`, `owner_id`, `importance`.
- Embeddings are generated by `agentsys.llm.embed_texts()` using
  `openai/text-embedding-3-small`.

Creation:

- Only `_reflect_and_save_memory()` creates long-term memory.
- It runs after `synthesize_node` completes, not after quick replies, failed
  tasks, cancelled tasks, or tasks paused at escalation.
- It calls `MEMORY_REFLECTION_PROMPT` with request text, tools used, and the
  first 500 chars of final outcome.
- The reflection schema can return:
  `worth_saving`, `kind` (`episodic`, `fact`, `preference`), `content`,
  `importance`.
- If worth saving, `long_term.add_memory()` writes to Chroma first and then
  Postgres.
- `long_term.prune_low_value_memories(owner_id)` runs after a save.

Retrieval:

- `sketch_node` unconditionally retrieves `k=3` memories for the original
  request.
- `agent_step_node` does not retrieve long-term memory.
- `retrieve_relevant()` queries Chroma with owner filter and optional kind
  filter.
- It requests up to `k * 3` candidates, filters below `similarity_floor=0.3`,
  and ranks by:

```text
weighted_score = 0.7 * similarity + 0.3 * (importance / 5)
```

- It updates Postgres `last_accessed_at` for returned ids if rows exist.

Lifecycle:

- `prune_low_value_memories(owner_id, keep_top_n=500)` keeps the highest
  `(importance, last_accessed_at)` rows per owner and deletes the rest from
  Postgres, then Chroma.
- There is no deduplication, merge, supersession, usage count, confidence,
  provenance beyond `task_id`, artifact reference, TTL, or manual correction
  path.

Current semantics:

- The system calls the kind `episodic`, but current reflection content is often
  a generalized lesson, not a true episode.
- `fact` and `preference` are closer to semantic memory.
- Current long-term memory is therefore mixed curated lessons, facts, and
  preferences. Do not rename it until ingestion and retrieval semantics are
  made explicit.

Current consistency gaps:

- `add_memory()` writes to Chroma before Postgres. A DB failure can leave an
  orphan vector.
- `retrieve_relevant()` returns Chroma documents even if the Postgres
  `MemoryEntry` row is missing; it only skips the `last_accessed_at` update.
- `prune_low_value_memories()` deletes Postgres before Chroma. A Chroma delete
  failure can leave stale retrievable vectors.

## 2. Current context construction flow

Current prompt flow by node:

- `triage_node` sends full reconstructed conversation, if any, plus the current
  turn.
- `quick_reply_node` sends full reconstructed conversation and the current
  turn. It performs no tools, subtasks, or memory writes.
- `sketch_node` sends static sketch instructions, tool descriptions, `k=3`
  retrieved long-term memories, and original request.
- `agent_step_node` sends:
  static instructions,
  tool descriptions,
  original request,
  full conversation history for continued tasks,
  current plan from latest `plan` trace span or sketch,
  prior subtask context from `_gather_prior_context`,
  dead-call prompt block from Redis,
  step budget numbers.
- `_execute_subtask` sends tool-selection prompt only on retry or when no
  preselected tool choice exists. It uses prior context and revision feedback.
- Reasoning-only subtasks send prior context and revision feedback.
- `_review_subtask` sends only the subtask description, tool used, tool success,
  and output, after deterministic verification has had the first chance.
- `_verify_goal_before_synthesis` sends conversation plus completed/recorded
  outputs only when deterministic goal verification returns `REVIEW`.
- `synthesize_node` sends conversation and completed subtask outputs after
  `artifacts.for_synthesis()` strips spill mechanics.
- `_reflect_and_save_memory` sends request, tools used, and outcome preview.

Current token controls:

- API request text is capped by `settings.max_request_text_length`.
- Prior subtask context uses recent-step/full and older-step/truncated policy.
- Tool outputs above `settings.max_tool_output_chars` are spilled to
  `_artifacts/` with a digest, preview, path, total chars, and hint.
- Artifact dereference via `file_io` read under `_artifacts/` bypasses spill but
  is capped by `settings.max_dereference_chars`.
- Live Redis events truncate payload shape through `events.truncate`.
- `LlmCall` records prompt tokens, completion tokens, cached prompt tokens, and
  derived cost.

What is not controlled today:

- full conversation history,
- memory block size,
- tool catalog token cost,
- RAG answer/source block size,
- prompt-level aggregate input budget,
- explicit model context windows,
- selected vs dropped context metrics.

## 3. What is already good and should remain

Keep these decisions:

- Postgres is the durable source of truth; LangGraph state stays tiny.
- Redis short-term memory is task-scoped scratch, not durable memory.
- Long-term memory is owner-scoped in both Postgres and Chroma metadata.
- The memory retrieval rank already blends similarity and importance.
- Reflection is best-effort and cannot fail an already completed task.
- Memory is curated rather than saving every completed task.
- `_gather_prior_context` uses recency-aware compaction and includes failed
  evidence.
- Artifact spill uses progressive disclosure: full original on disk, compact
  digest/preview in prompt, explicit file dereference only when needed.
- `artifacts.for_synthesis()` prevents internal artifact paths from leaking to
  end users.
- Dead-call and repeated-success ledgers stop tool loops that otherwise look
  like successful progress.
- Prompt construction already protects cache-friendly static prefix ordering in
  `AGENT_STEP_PROMPT` and `TOOL_SELECTION_PROMPT`.
- `LlmCall.cached_tokens` keeps "unknown" distinct from "zero cached".
- The deterministic eval gate can be reused to measure memory usefulness before
  adding heavier judge calls.

## 4. Existing problems/gaps

Memory and context gaps:

- No rolling conversation summary.
- Continued tasks send full history without a token threshold.
- Long-term memory is retrieved only during sketch, not during the step loop.
- Sketch retrieval is unconditional and fixed at `k=3`.
- Current reflection does not see full task evidence; it sees tools used and a
  short final outcome preview.
- No automatic memory extraction from ordinary follow-ups such as corrections,
  preferences, or explicit decisions.
- No deduplication or merge. Repeated reflections can create near-duplicates.
- No pinned decision semantics.
- No true episodic representation of "what happened during a task".
- No artifact-reference memory. Full artifacts should not be copied into
  semantic memory.
- No context builder that chooses among conversation, summary, memory, RAG, and
  tool results under one budget.
- No token budget manager with model context windows and output reservations.
- No memory usefulness eval.
- Chroma/Postgres consistency can drift because writes/deletes are not
  reconciled on retrieval.
- `short_term` scratch keys have no TTL and are only cleared on successful
  synthesis.

Tenancy gaps:

- Agent memory is user-isolated.
- Task, escalation, trace, artifact, and analytics endpoints are user-scoped.
- RAG remains a shared corpus, which is a separate known cross-tenant leak if
  multiple real users upload documents.

## 5. Proposed memory taxonomy

Do not map the 16 desired capabilities to 16 modules or stores.

Use these categories:

| Category | Current/future store | Meaning |
| --- | --- | --- |
| Working memory | Existing Redis scratch + Postgres task/subtask rows | Current task state, retries, dead calls, temporary session ids |
| Recent conversation | Existing `TaskMessage` + `TraceSpan` final answers | Last turns kept verbatim |
| Rolling summary | New fields on `Task`, not a new table | Structured compression of older turns in this task conversation |
| Episodic memory | Derived from existing task history, with small `MemoryEntry` pointer/summary when useful | What happened during a previous task |
| Semantic memory | Existing `MemoryEntry` evolved | Generalized reusable lessons/facts/preferences |
| Pinned decisions | Existing `MemoryEntry` evolved with kind/scope/importance | Durable decisions and constraints |
| Artifact references | Existing task workspace/artifacts API, referenced from memory metadata | Pointers to files/reports/tool outputs, not copied content |

The current `MemoryEntry.kind` values should expand rather than be replaced:

- `semantic`
- `episodic`
- `pinned_decision`
- `preference`
- `artifact_reference`

Keep existing `fact` as backward-compatible alias for `semantic` during
migration.

Scopes should reflect current tenancy:

- `task`: useful only inside one task.
- `conversation`: useful for this task thread/follow-up chain.
- `user`: useful across this user's future tasks.

Do not add `global` now. There is no global product requirement and it would
raise privacy and governance questions immediately.

Do not add `project` now. The repository has no `Project` or workspace tenant
table. Add it only when project tenancy exists.

## 6. Automatic memory-ingestion lifecycle

Automatic ingestion should be a deterministic harness around an LLM proposal:

```text
conversation/task event
  -> collect bounded evidence from existing rows
  -> LLM proposes memory candidates
  -> deterministic validation/classification
  -> exact dedupe
  -> semantic near-duplicate search
  -> STORE / MERGE / IGNORE
  -> embed if needed
  -> persist Postgres + Chroma
  -> trace what happened
```

Candidate fields the LLM may propose:

- `kind`: semantic, episodic, pinned_decision, preference, artifact_reference.
- `scope`: task, conversation, user.
- `content`: one or two dense sentences.
- `importance`: 1 to 5.
- `confidence`: 0.0 to 1.0.
- `source`: task id, message id, subtask ids, artifact paths if relevant.
- `merge_hint`: optional existing memory id if prompted with candidates.

Deterministic code must control:

- valid kind/scope values,
- owner id,
- source ids,
- whether eval tasks can write memory (default: no),
- whether failed/cancelled tasks can write memory (only if the lesson is about
  failure and the outcome is marked honestly),
- minimum confidence/importance thresholds,
- secret redaction,
- exact hash dedupe,
- merge vs create,
- Chroma metadata.

Smallest storage evolution:

- Keep `MemoryEntry`.
- Add `meta JSONB` for source/provenance/scope/confidence/artifact refs and
  normalized hash.
- Add `updated_at` for merge and supersession.
- Do not add a new memory table in 6B.

Why this is enough:

- `owner_id`, `task_id`, `kind`, `content`, `importance`, `created_at`, and
  `last_accessed_at` already exist.
- Chroma already stores document text and owner/kind metadata.
- The missing production-grade parts are provenance, scope, merge metadata, and
  update timestamp, not a second memory database.

## 7. Rolling-summary design

Desired behavior:

```text
recent messages
  + rolling summary of older messages
  + current turn
```

Storage:

- Add fields to `Task`, not a new table:
  - `rolling_summary JSONB | None`
  - `rolling_summary_version int`
  - `rolling_summary_updated_at datetime | None`
  - `rolling_summary_until datetime | None`

Summary shape:

```json
{
  "current_goal": "...",
  "important_decisions": [],
  "completed_work": [],
  "open_questions": [],
  "unresolved_failures": [],
  "constraints": [],
  "references": [],
  "artifact_refs": []
}
```

Trigger:

- At `_gather_conversation_history`, before constructing prompt text, estimate
  tokens for reconstructed conversation.
- If over `settings.conversation_summary_trigger_tokens`, summarize all turns
  older than the last `settings.conversation_recent_turns_full`.
- Keep recent turns verbatim.
- Originals remain in `TaskMessage` and `TraceSpan`; summary is only a lossy
  prompt view.

Initial config values:

- `conversation_recent_turns_full = 4`
- `conversation_summary_trigger_tokens = 3000`
- `conversation_summary_max_tokens = 900`

Failure handling:

- If summary generation fails, fall back to current full-history behavior for
  that turn and record a warning trace span.
- Never block a task on summary failure.

Versioning:

- Increment `rolling_summary_version` on successful update.
- Store `rolling_summary_until` so future updates only summarize newly old
  turns plus the previous summary.

Why not use `TraceSpan` only:

- A rolling summary is execution state, not telemetry. Trace spans can record
  the update, but `Task` should own the current summary.

## 8. Episodic-memory design

Target semantics:

```text
What happened during a previous task?
```

Existing rows already contain the episode source of truth:

- `Task`: goal, owner, final status/output.
- `Subtask`: ordered steps, status, output, success criteria.
- `ToolCall`: tool evidence and effect identity.
- `Escalation`: human pauses/decisions.
- `TraceSpan`: decisions/reviews/verification.
- artifacts API: files produced or spillover files.

Smallest representation:

- Do not duplicate full episodes into a new table.
- Create a compact `MemoryEntry` only when the episode is likely useful later.
- Store a short episode summary in `content`.
- Store structured references in `metadata`:
  - `scope: "user"` or `"conversation"`
  - `source_task_id`
  - `outcome: success | failed | cancelled | escalated`
  - `important_subtask_ids`
  - `artifact_refs`
  - `lesson_candidate_ids` if semantic lessons were promoted.

Episode example:

```text
Goal: Deploy FastAPI app.
Outcome: success.
Important events: localhost database failed; external DATABASE_URL fixed deployment.
Artifacts: deployment report.
```

Failed tasks may create episodic memory only when:

- the failure is meaningful and generalizable,
- the content labels the outcome as failed,
- the reflection is not just "task failed".

## 9. Semantic-memory design

Target semantics:

```text
Generalized reusable knowledge learned from prior experience.
```

The existing `MemoryEntry` already approximates semantic memory for `fact`,
`preference`, and generalized `episodic` reflections. Evolve it.

Promotion flow:

```text
episode evidence
  -> reflection proposes lesson
  -> deterministic filters:
       reusable?
       not task-only?
       not secret?
       sufficiently confident?
       duplicate/merge?
  -> semantic MemoryEntry
```

Semantic memory should be short, scoped, and evidence-backed:

- content: generalized lesson;
- metadata:
  - `scope`
  - `confidence`
  - `source_task_id`
  - `source_message_id` if from conversation
  - `supporting_artifacts`
  - `supersedes` / `superseded_by` when corrected.

Do not store large tool outputs as semantic memory. Store a lesson and an
artifact reference.

## 10. Pinned-decision design

Pinned decisions are durable facts/constraints that should not disappear
through summarization or decay.

Examples:

- "Do not implement Phase 6 memory features yet."
- "Postgres remains the durable source of truth."
- "Do not add global memory until there is a product requirement."

Use `MemoryEntry` with:

- `kind = "pinned_decision"`
- `importance = 5`
- `metadata.scope = "user"` or `"conversation"`
- `metadata.confidence`
- `metadata.source_task_id` / `source_message_id`
- `metadata.status = "active" | "superseded"`

Merge/update semantics:

- A new compatible statement reinforces the existing decision and updates
  metadata/evidence.
- A contradiction creates a candidate requiring explicit higher-confidence
  source or human confirmation before superseding.
- Pinned decisions do not auto-decay.

Do not create a separate pinned-decision table unless the product later needs
permissions, review workflow, or admin controls distinct from memory.

## 11. Artifact relationship

Artifacts are already first-class enough for Phase 6:

- `file_io` writes deliverables to the task workspace.
- `artifacts.spill()` writes oversized tool results under `_artifacts/`.
- `GET /v1/tasks/{task_id}/artifacts` lists deliverable vs spillover files.
- `GET /v1/tasks/{task_id}/artifacts/content` reads bounded file content with
  owner check and sandbox path resolution.

Memory should reference artifacts, not copy them.

Memory artifact metadata should contain:

- `task_id`
- `path` relative to task workspace
- `kind`: deliverable or spillover
- `bytes`
- optional `content_hash`
- optional `summary`

Rules:

- Deliverables may be referenced by episodic memory.
- Spillover may be referenced when it is the evidence for a lesson.
- Artifact content should enter semantic memory only as a distilled lesson.
- Artifact access must still route through existing task ownership checks.

## 12. Deduplication/merge strategy

Start simple.

Exact dedupe:

- Normalize content: lowercase, trim, collapse whitespace, strip punctuation
  that does not affect meaning.
- Compute a hash and store it in `MemoryEntry.meta.normalized_hash`.
- If owner/kind/scope/hash match, merge instead of create.

Near-duplicate merge:

- Before creating a memory, call existing Chroma retrieval with:
  - same owner,
  - same or compatible kind,
  - same scope where possible.
- Use a high similarity threshold, initially `0.88`, to detect likely
  duplicates.
- Deterministic merge if the new candidate is a restatement.
- If contradictory or lower confidence, preserve existing memory and record an
  ignored candidate trace.

Merge behavior:

- Keep the clearest content.
- Raise importance only when the new evidence justifies it.
- Append provenance in metadata.
- Update `updated_at`.
- Re-embed only if content changes materially.

Do not add clustering, graph memory, or a cross-encoder in 6B.

## 13. Retrieval/reranking design

Current retrieval is sketch-only. Phase 6C should introduce scoped retrieval
for the actual step loop and context builder.

Pipeline:

```text
current turn + current step
  -> decide whether memory is useful
  -> retrieve candidates by owner/scope/kind
  -> deterministic rank
  -> optional cheap LLM usefulness filter only if eval shows noise
  -> include top useful memories within budget
```

Initial ranking:

```text
score =
  0.55 * semantic_similarity
  + 0.25 * importance
  + 0.15 * recency
  + 0.05 * kind/scope boost
```

Use existing Chroma retrieval first; fetch Postgres rows for candidate metadata
before returning anything to the prompt. This also fixes stale/orphan Chroma
vectors.

Retrieval places:

- Keep sketch memory retrieval, but gate it.
- Add retrieval in `agent_step_node` through the context builder, keyed on the
  current turn and current plan/step state.
- Do not retrieve memory for quick replies unless the quick classifier is later
  expanded to "answer from memory"; today quick replies are intentionally
  limited to prior conversation.

## 14. Context-builder design

The context builder is the main Phase 6C component.

It should assemble a structured prompt input from available sources:

```text
System/static prompt
Tool descriptions
Current user message
Recent conversation
Rolling summary
Current task state
Prior step evidence
Pinned decisions
Relevant episodic memory
Relevant semantic memory
Relevant artifact references
RAG evidence
Tool results / spill digests
Dead-call hints
Budget/status values
```

But it must not include everything.

Priority order:

1. Must-have static instructions and tool schemas.
2. Current user turn / task objective.
3. Safety and pinned decisions relevant to the current user/task.
4. Current task state: plan, current step, verification failures, dead calls.
5. Recent conversation turns.
6. Rolling summary.
7. Recent/high-signal prior step evidence.
8. Relevant semantic/episodic memory.
9. RAG evidence.
10. Artifact summaries/references.
11. Optional background.

Truncation/drop rules:

- Never drop system/developer-equivalent safety text.
- Never drop the current user turn.
- Never drop pinned decisions that directly constrain the action.
- Prefer summary over old verbatim turns.
- Prefer artifact references plus digest over full artifact text.
- Drop low-relevance memories before dropping recent conversation.
- Drop RAG chunks not cited or not relevant before dropping task evidence.
- Emit structured metrics describing what was selected and dropped.

Implementation location:

- Create one module, `src/agentsys/context.py`, in Phase 6C.
- Do not create one builder per node.
- Refactor node prompt assembly gradually into this module.

## 15. Token-budget strategy

Use explicit budgets instead of scattered hardcoded character caps.

Concept:

```text
input_budget = model_context_window - reserved_output_tokens
```

Add settings:

- `model_context_windows` mapping or function.
- `reserved_output_tokens_by_purpose`.
- `context_budget_default_tokens`.
- `conversation_recent_turns_full`.
- `memory_context_budget_tokens`.
- `rag_context_budget_tokens`.
- `tool_result_context_budget_tokens`.

Initial allocation for `agent_step`:

| Block | Rule |
| --- | --- |
| Static prompt + tool descriptions | measured first, protected |
| Current request/current turn | protected |
| Plan + task state + dead calls | protected, compact |
| Recent conversation | bounded, last N turns |
| Rolling summary | bounded |
| Prior step context | recency-windowed |
| Pinned decisions | high priority, small |
| Long-term memories | bounded, rank sorted |
| RAG evidence | bounded, rank/citation sorted |
| Artifact refs/digests | bounded |

Use `tiktoken`, already present in `requirements.txt`, for approximate counting.
Provider-reported `LlmCall.prompt_tokens` remains ground truth after the call.

Graceful degradation:

- If under budget, send selected context unchanged.
- If over budget, shrink optional blocks in priority order.
- If still over budget, summarize/compress lossy blocks.
- If still over budget, fail with a clear escalation rather than sending a
  malformed or silently incomplete prompt for high-risk actions.

## 16. Headroom/context-compression integration point

Headroom is a context compression layer, not the memory system.

Current public Headroom docs describe:

- live-zone-only compression of newest user/tool content;
- preserving older turns, tools, and system prompt byte-for-byte to protect
  provider cache hot zones;
- reversible compression through CCR, where originals remain retrievable;
- entry points such as proxy, SDK/function call, integrations, and MCP;
- compression of tool outputs, logs, files, RAG chunks, and conversation
  history.

Recommended AgentForge boundary:

```text
memory retrieval
  -> context builder
  -> optional compression adapter
  -> token budget final check
  -> LLM
```

Data that should never be lossy-compressed:

- system/developer-equivalent instructions,
- tool schemas,
- current user request,
- policy decisions and approval snapshots,
- exact tool arguments for side effects,
- pinned safety constraints,
- audit/effect identities.

Data that can be compressed:

- long tool outputs,
- logs,
- RAG chunks,
- older conversation text after summary has preserved decisions,
- artifact previews/digests.

Do not install Headroom in 6B. In 6D, add a small adapter interface first:

```python
class ContextCompressor:
    def compress(blocks: list[ContextBlock], budget: TokenBudget) -> CompressionResult: ...
```

The adapter can initially be a no-op. A Headroom implementation can be added
behind that interface only after context-builder metrics prove which blocks are
worth compressing.

## 17. Prompt-caching strategy

Current good behavior:

- `AGENT_STEP_PROMPT` and `TOOL_SELECTION_PROMPT` intentionally put static
  instructions and tool descriptions before dynamic task context.
- `LlmCall.cached_tokens` is recorded.
- `pricing.py` understands cached input token pricing.

Phase 6 strategy:

- Preserve stable prefixes: system text, tool schemas, static policy/agent
  instructions.
- Put dynamic context after a clear delimiter.
- Keep selected memory/RAG/tool results after the stable prefix.
- Do not inject timestamps, UUIDs, or volatile metrics above tool schemas.
- Avoid provider-specific cache controls in node code. If needed, hide them in
  `llm.py` or the future context/compression adapter.
- Track cache instability as a metric before optimizing for it.

## 18. Memory lifecycle/pruning

Lifecycle:

```text
CREATE
MERGE
RETRIEVE
REINFORCE
DECAY
ARCHIVE / DELETE
```

What exists:

- create,
- retrieve,
- prune by lowest importance/last access over 500 entries.

Add later:

- reinforce: increment retrieval/use metadata only when a memory is actually
  included in prompt or cited as useful;
- decay: reduce priority for low-importance memories never retrieved;
- archive/supersede: mark stale/corrected memories inactive before deleting;
- delete: remove from Postgres and Chroma with reconciliation.

Pruning rules:

- Pinned decisions do not auto-decay.
- Low importance + never retrieved + old can decay/archive.
- Task/conversation scoped memories can expire after task closure unless pinned.
- Superseded decisions should remain for audit/provenance but not be retrieved
  by default.

Do not add a background pruning job in 6B. Run lightweight prune after writes,
as current code already does, and add a manual/admin maintenance command later
if needed.

## 19. Privacy/tenancy

Current protections:

- `Task.owner_id` isolates tasks.
- `MemoryEntry.owner_id` isolates Postgres memory rows.
- Chroma memory metadata also includes `owner_id`, and retrieval filters on it.
- API endpoints for tasks, escalations, traces, artifacts, analytics, and
  memory check the signed-in user.
- Artifact reads resolve paths inside a task workspace and verify task
  ownership before reading.

Current gaps:

- Chroma/Postgres consistency gaps can surface deleted/orphaned vectors.
- `retrieve_relevant()` should verify returned ids against Postgres owner rows
  before returning prompt content.
- RAG documents are not user-isolated in `src/rag`.
- `MemoryEntry.kind` is free-form; future retrieval must not trust arbitrary
  kind/scope metadata without validation.

Phase 6 rules:

- Every memory write must take owner id from the server-side task/user, never
  from model output.
- Every vector metadata row must include owner id and scope.
- Every retrieval must filter by owner id at vector search and verify against
  Postgres.
- Eval tasks must not write user memory unless explicitly testing memory in an
  isolated eval owner.
- Artifact references in memory must still dereference through existing
  artifact ownership checks.

## Ponytail test

### New table?

No new memory or episode table. Existing task history is the episode source of
truth, and existing `MemoryEntry` can carry compact reusable memory with a
small `meta` expansion.

### New module?

Two eventual modules survive the test:

- `memory/curation.py`: existing `long_term.py` stores/retrieves memories but
  should not grow LLM extraction, validation, dedupe, and merge orchestration.
- `context.py`: prompt context selection is currently spread across nodes and
  cannot support global token budgets cleanly in-place.

No separate modules for episodic, semantic, pinned, dedupe, reranking, summary,
or lifecycle in the first implementation.

No new dependency in 6B or 6C. `tiktoken` already exists. Headroom remains a
6D adapter candidate, not a memory dependency.

summary adds a model call only when a threshold is exceeded and fails open to
current behavior. Do not add separate model calls for dedupe, reranking, and
importance until deterministic scoring proves insufficient.

No background job in 6B. Prune after writes, as today. Add maintenance only
after lifecycle metrics show it is needed.
